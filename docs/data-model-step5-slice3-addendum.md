# 第 5 步切片 3 数据模型补充：直播状态

本文件只记录第 5 步切片 3 的增量，不回写 `docs/data-model-v1.md`，不改变已有航次、出航打卡或返航状态的含义。

迁移：`server/migrations/020_step5_live_status.sql`。

## 船长抖音主页

`captain_profiles` 增加可空字段 `douyin_handle` 和 `douyin_profile_url`。两者必须同时为空或同时填写。服务端只接受抖音域名下的 HTTPS 个人主页链接；这里仅保存船长自报的账号与链接，不做 OAuth 或平台账号核验。

解绑时锁定船长档案并再次确认没有活动直播，避免解绑与开播并发后留下空链接的直播入口。

## 直播会话

`step5_live_sessions` 按航次追加会话记录：船长、航次、开始时间、结束时间及结束原因。结束原因为船长手动结束、返航打卡或管理员核实虚假标记。部分唯一索引保证每个航次最多一个未结束会话。

开播路由在同一事务中锁定航次与船长档案，并要求船长已审核、账号和主页已绑定、航次状态为 `in_progress`、存在本船长的 `departed` 打卡且没有 `returned` 打卡。结束路由使用相同航次与打卡门禁。返航打卡在 Step 4 原有事务中自动结束活动会话。

查询时只有满足上述有效航次状态、且会话未结束的记录才生成直播徽章与跳转链接。客户端和服务端都不接收、转发或存储视频。

## 举报与处理状态

`step5_live_reports` 保存举报人、航次、对应会话、预置理由、可选备注、提交时间和处理状态。唯一约束 `(departure_id, reporter_user_id)` 确保同一用户对同一航次只产生一条举报事实；重复提交返回原记录，不增加计数。

处理状态为 `pending`、`false_verified` 或 `not_false`。管理员使用环境口令接口处理；不存在自动判断或申诉状态。

处理为 `false_verified` 时，在同一事务中结束该次会话，并向 `step5_captain_live_incident_facts` 插入一条船长事实。该事实只保存船长、航次、核实时间和固定结果码；公开接口只返回日期、航次与核实结果，不返回举报人、备注或评分，也不计算排名。
